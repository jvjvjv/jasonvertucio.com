## 6. Production migration

Ran live on 2026-09-08, materially differently from the script below — captured here for the record rather than rewritten as if it went to plan.

- [x] 6.1 Schedule maintenance window and run `php artisan down` — **done, though out of order: the developer ran `php artisan migrate` directly over SSH before maintenance mode was confirmed on; `php artisan down` was applied partway through once the incident was recognized**
- [~] 6.2 Take an external SQL dump of `canvas_*` tables and back up `storage/app/public/canvas` media — **skipped**. Not needed for the `canvas_*` tables (the rename-not-drop design meant `canvas_v6_backup_*` served as the real safety net throughout). Consequently a separate, pre-existing, unrelated incident went unnoticed until tonight: `storage/app/public/{canvas,wink}` — real uploaded images referenced by 17 posts — has been missing from the server filesystem since ~2026-09-03 (an earlier, unrelated deploy), because `prod.sh`'s `rsync --delete-after` does not exclude `storage/app/public/*`. A storage backup here would not have caught that (it already happened days earlier) but is still worth doing before future migrations. **Follow-up, not part of this change**: fix `prod.sh` to protect `storage/app/public/*`, and attempt image recovery for the 17 affected posts (Wayback Machine has archived several of the post pages themselves, which may hold the images).
- [x] 6.3 Deploy the v7 composer/config/code changes — **done**, though via direct `scp` of the two migration files plus manual `composer install`/asset steps rather than a full `./prod.sh` run, once the incident was underway
- [x] 6.4 Run `php artisan migrate` against `jasonvertucio` — **done, in two attempts**. First attempt failed on `SQLSTATE[22001]: Data too long for column 'featured_image'` — production's real `featured_image` values (long CDN URLs) exceeded the `VARCHAR(255)` this change's create-table migration had copied from Canvas's own vendor migration. Because the reconciliation migration wasn't transaction-wrapped, the partial inserts from that failure were left in place, and a naive retry then hit duplicate-key errors on top. Fixed in `2026_09_08_160001_create_canvas_v7_tables.php` (widened `featured_image`/`featured_image_caption`/`canvas_users.avatar`/`canvas_users.website`/`canvas_media.caption` to `text()`) and `2026_09_08_160002_migrate_canvas_v6_content_to_v7.php` (wrapped all inserts in `DB::transaction()`, added a `MAX_FEATURED_IMAGE_LENGTH` guard that nulls out and logs anything absurdly long rather than storing or choking on an accidental paste). Both fixes rehearsed against `wink` with real reproductions of both failure modes before redeploying. Second attempt on production succeeded: all 36 posts, 9 topics, 19 tags recovered.
- [x] 6.5 Verify row counts — **done**: posts 36/36, topics 9/9, tags 19/19 against the `canvas_v6_backup_*` baseline. `canvas_users`: the one backup row with a null v6 role (`admin@mail.com`) was correctly skipped and logged per the migration's documented decision.
- [x] 6.6 Grant admin access — **not needed**: the reconciliation migration already carries `canvas_users` access rows over from the backup (matched by email), so the existing admin's access was already correct after 6.4. Confirmed working via successful `/canvas` access after the asset fix below.
- [~] 6.7 Smoke-test — **partially done, with one real bug caught and fixed along the way**: `/canvas` initially loaded blank with no server error, because the package upgrade was never followed by `php artisan canvas:install` (or the equivalent `vendor:publish`), so the SPA was still serving v6's stale compiled assets against the v7 backend. Running `canvas:install` directly hung indefinitely — it shells out to `migrate --path=... --force=false` via `callSilent()`, which suppresses the production confirmation prompt's *text* but still blocks on stdin waiting for an answer; Ctrl+C to abort is safe (that inner migration is a no-op regardless). Resolved instead via `php artisan vendor:publish --tag=canvas-assets --force` + `php artisan storage:link`, after which `/canvas` loaded correctly. `/blog` index and post pages confirmed rendering. Comment submission, `/admin/comments`, and the 403-for-no-access case were not separately re-verified tonight.
