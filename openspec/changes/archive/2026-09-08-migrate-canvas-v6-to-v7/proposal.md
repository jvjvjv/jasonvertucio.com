## Why

Canvas v7.0.0 is a ground-up rewrite (released 2026-07-26) that removes Canvas's own authentication system entirely and hands identity ownership to the host application. This site already works around v6's Canvas-owned `canvas` guard with a bespoke `CanvasServiceProvider` guard override and a `SyncCanvasAuth` middleware just to make Canvas trust the app's own `User` model — exactly the seam v7 is designed to eliminate natively. Staying on v6 means carrying that workaround indefinitely and missing v7's supported multi-role access model (`canvas_users` as a pure access/role row against the host user), new post lifecycle events, and continued Laravel 12/13 + PHP 8.3+ support. v7 is a clean-break upgrade with no in-place data migration path, so this needs to be planned deliberately rather than done as a routine `composer update`.

## What Changes

- **BREAKING**: Replace `austintoddj/canvas` `^6.0.56` with `^7.0`. Canvas no longer owns authentication — the host `web` guard is authoritative, and Canvas checks a `canvas_users` access row for authorization instead of maintaining its own guard/credentials.
- **BREAKING**: Remove the custom `canvas` auth guard override in `app/Providers/CanvasServiceProvider.php` and delete `app/Http/Middleware/SyncCanvasAuth.php` — this workaround becomes redundant/incompatible with v7's host-owned auth model.
- **BREAKING**: Update `config/canvas.php` to v7's schema: `user_model` replaces `user`, `guard` config key added, the `auth` middleware entry and the entire `user` config block are removed.
- **BREAKING**: `canvas_posts_topics` multi-topic pivot is removed in favor of a single `topic_id` FK on `canvas_posts`. `App\Models\CanvasPostsTopics` (and its usage, if any beyond the pivot itself) is retired; each post must resolve to exactly one topic before migration.
- **BREAKING**: `canvas_users` schema changes to a host FK (`user_id` → `users.id`, `nullOnDelete`) and drops Canvas-managed passwords/soft-deletes. Canvas's own upgrade guide's prescribed path involves dropping the old `canvas_*` tables outright; **this project does not do that**. Instead, a versioned Laravel migration renames the existing `canvas_*` tables to `canvas_v6_backup_*` (preserving every row) before Canvas's own v7 migrations create fresh tables of the original names, and a second versioned migration reconciles existing posts, tags, topics, and comment linkage (`comments.canvas_post_id` in this app) from the backup tables into the new schema. No table is dropped and no row is deleted as part of this change — the backup tables remain in the database, and removing them later is a separate decision left entirely to the developer.
- Update the `@ifcanvasauthenticated` Blade directive (`app/Providers/BladeServiceProvider.php`) to check host-app authentication plus `canvas_users` access instead of `Auth::guard('canvas')`, which no longer exists.
- Replace removed/renamed Canvas artisan usage: `canvas:user` is gone; adopt `canvas:make-admin`, `canvas:assign-role`, `canvas:remove-access`, `canvas:users` as needed. Audit `app/Console/Commands/CreateUserCommand.php` and `ChangeUserPasswordCommand.php`, which alias `Canvas\Models\User as CanvasUser` — that model's role in v7 (host user vs. `Canvas\Models\CanvasUser` access row) must be re-verified.
- Optionally adopt `Canvas\Concerns\HasCanvasAccess` on `App\Models\User` for role accessors (`isAdmin()`, `isEditor()`, `isContributor()`) if it simplifies existing role checks — evaluate during design, not required.
- Adopt v7's new `PostPublished`/`PostScheduled`/`PostUpdated`/`PostUnpublished`/`PostDeleted` lifecycle events where useful (e.g., for the AI-persona resume/blog tooling or comment notification patterns) — evaluate during design, not required for parity.
- Update media/storage handling for v7's URL format changes (root-relative public-disk URLs vs. absolute for remote/S3) if `resources/config/config.json`, blog views, or the MCP `GetRecentBlogPostsTool` assume v6's URL shape.
- Re-verify the `/canvas` catch-all route behavior (documented in `routes/admin.php` and `blog-comment-moderation` spec) still holds under v7's routing.

## Capabilities

### New Capabilities
- `canvas-v7-blog-platform-integration`: Defines the post-migration behavior of the Canvas blog platform integration — who can access `/canvas` and how (host auth + `canvas_users` role row, no separate `canvas` guard), that existing published posts/tags/topics/comment linkage remain intact and publicly viewable after the schema migration, and that the site's own comment system and admin panel continue to function unaffected by the Canvas auth rewrite.

### Modified Capabilities
- None. `blog-comment-moderation`'s existing requirement about the `/canvas` catch-all not swallowing `/admin/comments` is a routing behavior expected to hold under v7 as well; it will be re-verified as a task, not changed as a requirement. No other existing spec encodes Canvas's internal auth mechanics.

## Impact

- **Dependency**: `composer.json` (`austintoddj/canvas` `^6.0.56` → `^7.0`), `composer.lock`.
- **Config**: `config/canvas.php` (schema rewrite: `user_model`, `guard`, `middleware`, `locales`; removal of `user` block and `auth` middleware entry).
- **Removed**: `app/Http/Middleware/SyncCanvasAuth.php`; the custom `canvas` guard override in `app/Providers/CanvasServiceProvider.php`; `App\Models\CanvasPostsTopics` pivot usage (pending confirmation it isn't relied on elsewhere).
- **Modified code**: `app/Providers/CanvasServiceProvider.php`, `app/Providers/BladeServiceProvider.php` (`@ifcanvasauthenticated`), `app/Console/Commands/CreateUserCommand.php`, `app/Console/Commands/ChangeUserPasswordCommand.php`, `app/Http/Controllers/BlogController.php`, `app/Http/Controllers/HomeController.php`, `app/View/Components/LatestBlog.php`, `app/View/Components/CommentThread.php`, `app/Models/Comment.php`, `app/Http/Requests/StoreCommentRequest.php`, `database/factories/CommentFactory.php`, `app/Services/Mcp/Tools/ChatBot/GetRecentBlogPostsTool.php`.
- **Database**: all `canvas_*` tables (`canvas_posts`, `canvas_posts_tags`, `canvas_posts_topics`, `canvas_tags`, `canvas_topics`, `canvas_users`, `canvas_views`, `canvas_visits`) are renamed to `canvas_v6_backup_*` by a versioned migration — never dropped or deleted — before v7's own migrations create fresh `canvas_*` tables; a second versioned migration reconciles content from the backup tables into the new schema. App-side migrations that touch Canvas tables (`add_post_reference_to_comments`, `add_canvas_fields_to_users_table`, `add_fulltext_indexes_to_canvas_posts_table`, `correct_comments_post_id_type`) must be reconciled against the new schema. Must run against both the `jasonvertucio` (dev) and `wink` (test, per `phpunit.xml`) databases.
- **Data migration risk**: existing live blog posts, tags, topics, and the comment system's `canvas_post_id` linkage must survive the rename/reconcile cycle without data loss — mitigated by never dropping the original tables (they persist as `canvas_v6_backup_*` for the developer to remove on their own schedule, if ever) and by expressing every step as a reviewable, rollback-able Laravel migration rather than an ad-hoc destructive command; see design.md for the full procedure.
- **Deployment**: production `queue:work` restart and `composer install && php artisan optimize:clear` per standard deploy flow; this change additionally requires running `canvas:install` and re-running the data reconciliation step during the deploy window (likely requiring brief downtime or a maintenance mode for the blog/admin/comments-affected time window).
- **Tests**: `tests/` covering blog rendering (`BlogController`), comment submission/moderation, and the AI persona's `GetRecentBlogPostsTool` all touch `Canvas\Models\Post` and must be re-run/updated against the new schema and auth model.
