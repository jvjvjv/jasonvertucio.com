## Context

See `proposal.md` for motivation. Key constraints shaping this design:

- Canvas v7 provides **no in-place migration** from v6 — its own upgrade guide's prescribed path is: back up, drop `canvas_*` tables, remove Canvas's rows from the host `migrations` table, run `canvas:install` fresh. There is no first-party importer for v6 content into v7's schema. **This project does not drop or delete anything as an ad-hoc/manual step.** Every schema change — including retiring the old `canvas_*` tables — is expressed as a versioned Laravel migration file, reviewed and run by the developer via `php artisan migrate`. No table is dropped and no rows are deleted by an agent running commands directly; see Decisions below for the rename-not-drop approach.
- This app already carries a v6 workaround (`CanvasServiceProvider`'s guard override + `SyncCanvasAuth` middleware) that exists specifically to make Canvas trust the host `User` model — the exact thing v7 does natively via `config('canvas.user_model')` and a `canvas_users` access row. That workaround must come out, not be adapted.
- Content keys (`canvas_posts.id`, `canvas_tags.id`, `canvas_topics.id`) stay UUID in both v6 and v7, which is what makes a scripted re-import tractable instead of a full data-mapping exercise.
- The app has its own migrations layered on top of Canvas's tables (`add_post_reference_to_comments`, `add_canvas_fields_to_users_table`, `add_fulltext_indexes_to_canvas_posts_table`, `correct_comments_post_id_type`) and a `comments.canvas_post_id` FK that must keep pointing at the right post after the drop/recreate.
- Two databases are in play per `CLAUDE.md`: `jasonvertucio` (dev/prod-shaped) and `wink` (test, pinned in `phpunit.xml`). Both need the migration exercised.

## Goals / Non-Goals

**Goals:**
- Land on Canvas v7 with the host `web` guard as the sole source of authentication for `/canvas`, matching v7's intended architecture rather than re-building the v6 workaround on top of it.
- Preserve every existing published post, its tags, one topic per post, and all existing comment linkage, with zero visible regression on `/blog` or individual post pages.
- Remove now-dead code (`SyncCanvasAuth`, the custom guard override, any `CanvasPostsTopics` pivot usage) rather than leaving it in place unused.
- Keep the migration scriptable and repeatable so it can be rehearsed against `wink` (test) before touching the dev/prod database.
- Never drop a table or delete rows as an ad-hoc command. Every step that retires or restructures a `canvas_*` table is a checked-in Laravel migration file that the developer reviews before running, so the change is reversible and auditable through normal migration tooling (`php artisan migrate` / `migrate:rollback`).

**Non-Goals:**
- Adopting `Canvas\Concerns\HasCanvasAccess` on `User`, or wiring the new `PostPublished`/`PostScheduled`/`PostUpdated`/`PostUnpublished`/`PostDeleted` events into notification or AI-persona flows. Both are valuable follow-ups but not required for parity; they're called out in the proposal as evaluate-later, not committed here.
- Changing any public-facing blog UI/UX or comment system behavior — this is a platform/infra migration, not a feature change.
- Replaying Canvas's own view/analytics history (`canvas_views`, `canvas_visits`) into v7's schema — these are ephemeral engagement metrics, not content. They are still preserved (renamed to `canvas_v6_backup_*`, never dropped, per the Decisions below), but the reconciliation migration does not attempt to reimport historical view counts into v7's schema unless v7's shape happens to make that trivial (assess when the v7 schema is in hand; not a blocker either way).

## Decisions

**Decision: Canvas v7's own migration is incompatible with this app's UUID-keyed `users` table — replace it with a host-owned migration, don't run it.**
Discovered during implementation (not in the original upgrade guide): `App\Models\User` uses `HasUuids`, and `users.id` is `char(36)`. Canvas v7's vendor migration (`vendor/austintoddj/canvas/database/migrations/2020_09_21_000000_create_canvas_tables.php`) declares every `user_id` FK column as `$table->foreignId('user_id')` (an `unsignedBigInteger`) with a real FK constraint to `users.id` — on `canvas_topics`, `canvas_posts`, `canvas_media`, and `canvas_users` (where it's the primary key). This fails at FK-creation time against a `char(36)` column. Canvas offers no publish tag for its migration (it's loaded directly via `loadMigrationsFrom`), so there's no supported override point.
Chosen approach: a host-owned migration creates the full v7 table set (`canvas_topics`, `canvas_posts`, `canvas_tags`, `canvas_posts_tags`, `canvas_views`, `canvas_visits`, `canvas_users`, `canvas_media`, `canvas_settings`) with the exact same shape Canvas v7 expects, except every `user_id` column is `foreignUuid('user_id')` instead of `foreignId('user_id')`, matching `users.id`. No "fake migrate" bookkeeping trick is actually needed: Canvas ships the identically-named migration file (`2020_09_21_000000_create_canvas_tables.php`) in both v6 and v7, and this app's `migrations` table already has that exact filename recorded (batch 6, from the original v6 install) — Laravel's migrator will skip it automatically regardless of which version's content is on disk. That also confirms it will never create v7's new tables (`canvas_media`, `canvas_settings`) either, so the host-owned migration is fully responsible for the entire table set, not just the `user_id` columns. Alternative considered: forking/composer-patching the vendor migration file directly — rejected since the host-owned-migration approach keeps the vendor package byte-for-byte unpatched (lower maintenance burden across future Canvas point releases) while achieving the identical resulting schema.

**Decision: Work around Canvas's `'user_id' => 'integer'` model casts in our own code via `getRawOriginal()`, accept the admin-SPA display limitation.**
All five Canvas v7 models (`Post`, `Tag`, `Topic`, `Media`, `CanvasUser`) cast `user_id` to PHP `integer`, which would silently truncate a UUID string when read through the normal Eloquent attribute (`$post->user_id`, or the `user()`/`topic()` relations that build their query from the cast value). This app's own code (`BlogController`, `HomeController`, `LatestBlog`, `GetRecentBlogPostsTool`) will read the correct value via `$post->getRawOriginal('user_id')` and resolve the host `App\Models\User` directly, rather than relying on Canvas's `Post::user()` relation — this needs no vendor changes. Canvas's own admin-panel controllers (`PostController`, `MediaController`, etc.) use the base model classes directly with no swap point, so their internal author-related display inside `/canvas` may still misrender. Accepted trade-off: the underlying data is never actually corrupted (raw DB values stay correct `char(36)` UUIDs; only a PHP-level read-side cast is wrong), core auth gating (`Authorize`/`EagerLoadCanvasUser` middleware) is unaffected since those use raw query-builder `where()`/`find()` comparisons that don't go through the cast, and this is a personal blog with a small number of Canvas admins — full correctness would require a `composer-patches`-based vendor patch across 5 files, revisited only if this proves disruptive in practice.

**Decision: `canvas_users` rows with a null v6 `role` are not carried over.**
v7's `canvas_users.role` column is `tinyInteger` with no `->nullable()` — presence of a `canvas_users` row *is* access under v7's model, there's no "row exists but no role" state like v6 had. One of the two existing rows (`admin@mail.com`) has `role = null` in v6, which reads as an inactive/never-granted-access row. The reconciliation migration skips rows with a null role rather than defaulting them to a role; this is logged for developer review rather than silently applied, matching the topic-collapse logging pattern below.

**Decision: Rename the v6 `canvas_*` tables out of the way via a migration, never `DROP` them.**
Canvas's own upgrade guide says to drop `canvas_*` tables before running `canvas:install`, because v7's migrations create tables of the same name. Instead, a dedicated migration (`rename_canvas_v6_tables_to_backup`) uses `Schema::rename()` to move each `canvas_posts`, `canvas_posts_tags`, `canvas_posts_topics`, `canvas_tags`, `canvas_topics`, `canvas_users`, `canvas_views`, `canvas_visits` to a `canvas_v6_backup_*` name (e.g. `canvas_v6_backup_posts`), keeping every row. This clears the table names v7's own migrations need without deleting anything — `canvas:install`'s migrations can then create fresh `canvas_*` tables alongside the untouched backups. Nothing is ever `DROP`ped or `DELETE`d as part of this migration; the backup tables are left in the database indefinitely and it is entirely the developer's call, on their own schedule and outside this change, whether to ever remove them.

**Decision: Write a Laravel migration/reconciliation step rather than hand-editing SQL or running ad-hoc commands.**
A dedicated migration (`migrate_canvas_v6_content_to_v7`, run via `php artisan migrate` after the rename migration and the host-owned table-creation migration described below) reads from the `canvas_v6_backup_*` tables and inserts corresponding v7 rows for each post/tag/topic/user-access record, preserving post/tag/topic UUIDs so `comments.canvas_post_id` needs no rewriting. `canvas_users` rows are mapped by joining v6's `canvas_users.email` to the host `users.email`, since v6's `canvas_users.id` (its own UUID) has no relationship to the host `users.id` — only email ties the two together in this app's data. Because it is a normal migration file, it is reviewed like any other schema change and only ever executed by the developer running `php artisan migrate` — never by an agent invoking raw SQL against the database directly. Alternative considered: an Artisan command instead of a migration — rejected because a migration is naturally idempotent-checked by Laravel's migration table, versioned alongside the other migrations it depends on, and reviewable via the same `php artisan migrate:status` / `--pretend` tooling the developer already trusts.

**Decision: Resolve multi-topic posts to a single topic deterministically; verified against real data that this collapse never actually happens today.**
`canvas_posts_topics` carries no ordering column (no `id`, no `created_at` — just `post_id`/`topic_id` with a unique index), so "first-assigned" isn't recoverable from the data. The reconciliation migration instead picks the lowest `topic_id` (a stable, arbitrary-but-deterministic tie-break) when a post has more than one, and logs every such case via `Log::info()`. In this app's actual data (checked during implementation) zero posts currently have more than one topic and five have none — so this collapse logic exists for robustness but isn't expected to change anything real. Alternative considered: prompt per-post interactively — rejected as impractical for a scripted, repeatable migration.

**Decision: Post/tag/topic `user_id` values need no remapping; only `canvas_users` does.**
Verified during implementation: this app has a single blog author, and every `canvas_posts`/`canvas_tags`/`canvas_topics` row's `user_id` already equals a valid host `users.id` directly (confirmed via `information_schema` and direct row inspection) — content tables carry the value straight across unchanged. `canvas_users` (the access/role table) is different: it's rebuilt from the `canvas_v6_backup_users` table joined to host `users` by **email** (not by the old `canvas_users.id`, which is a separate identity space from `users.id` even though it coincidentally matches for the one account that has both). A backup row with no matching host email, or a null v6 `role`, is skipped and logged rather than guessed at.

**Decision: Delete `SyncCanvasAuth` and the `CanvasServiceProvider` guard override outright, don't feature-flag them.**
v7 makes them structurally unnecessary (host guard is authoritative, no separate `canvas` guard to sync into). Keeping them behind a flag would mean maintaining two auth models during a transition that has no rollback-in-place story anyway (see Migration Plan). Update `@ifcanvasauthenticated` in `BladeServiceProvider` to check host auth (`Auth::check()`) plus a `canvas_users` row lookup (via whatever v7 exposes — `CanvasUser::query()->where('user_id', ...)->exists()` or the `HasCanvasAccess`-equivalent helper if adopting it turns out cheap during implementation) instead of `Auth::guard('canvas')`.

**Decision: Run the migration during a short maintenance window, not live.**
Because the `canvas_*` drop/recreate is not atomic with respect to comment linkage and topic collapsing, doing this against a live site risks a comment landing on a half-migrated post. A brief maintenance-mode window (`php artisan down` / `up`) bounds that risk. Alternative considered: blue-green with a shadow database — rejected as disproportionate for a personal site's traffic/risk profile.

**Discovery: v6's `Post::topic()` was a mislabeled `belongsToMany`; v7 fixed it to a real `belongsTo`.**
v6's own source had a `topic()` method (singular name) implemented as `belongsToMany`, with a `// TODO: This should be a belongsTo() relationship?` comment acknowledging the bug. This app's code was written against that buggy v6 shape (`Post::with(['user','tags','topic'])`, `$post->topic->first()?->name` in `GetRecentBlogPostsTool`). v7 fixed it to a genuine `belongsTo`, so `->first()` on a single model fatals. Fixed in `GetRecentBlogPostsTool` (`$post->topic?->name`, plus adding `topic_id` to its explicit column `->get([...])` list so eager-loading the FK-based relation actually resolves). No blade template touches `$post->topic` at all, so this was otherwise invisible.

## Risks / Trade-offs

- **[Risk] Multi-topic posts silently lose a topic assignment** → Mitigation: the reconciliation migration's per-post topic-collapse log is reviewed by the developer before the maintenance window closes; any post needing a different topic than "first-assigned" is corrected manually post-migration.
- **[Risk] `comments.canvas_post_id` FK breaks if UUIDs don't carry over cleanly** → Mitigation: reconciliation migration explicitly re-inserts posts with their original UUID primary keys (not new ones), verified by a row-count and spot-check comparison (pre vs. post) as an explicit step before comments are trusted.
- **[Risk] No first-party rollback if the v7 install misbehaves in production** → Mitigation: because the v6 tables are renamed (`canvas_v6_backup_*`), not dropped, rollback is `php artisan migrate:rollback` on the reconciliation and rename migrations plus reverting the composer/config/code changes — the original data is still sitting in the database under its backup name, no restore-from-dump needed as the primary path (an external backup of `storage/app/public/canvas` media is still taken as a secondary safety net).
- **[Risk] `CanvasPostsTopics` pivot model may have usages beyond the pivot table itself** (unconfirmed by exploration) → Mitigation: grep for `CanvasPostsTopics` usages as an explicit early task before removing it, not assumed safe.
- **[Trade-off] Losing `canvas_views`/`canvas_visits` history** → Not lost: these tables are renamed to `canvas_v6_backup_views`/`canvas_v6_backup_visits` like everything else, not dropped; the reconciliation migration simply does not replay them into v7's schema unless that turns out to be trivial. The data remains in the database for the developer to deal with later, on their own terms.

## Migration Plan

All destructive-looking steps below (renaming old tables, inserting reconciled data) are ordinary Laravel migration files, checked into `database/migrations/`, reviewed like any other PR, and executed only by the developer running `php artisan migrate`. Nothing is dropped, deleted, or run ad hoc.

1. Rehearse the full rename/reinstall/reconcile procedure against the `wink` test database first by running the new migrations there; confirm via `php artisan test` (comment + blog feature tests) that post/tag/topic/comment behavior is unchanged.
2. Schedule a maintenance window; `php artisan down`.
3. As an extra safety net (belt-and-suspenders on top of the rename-not-drop migrations), take an external SQL dump of `canvas_*` tables and back up `storage/app/public/canvas` media on the dev/prod database.
4. `composer require austintoddj/canvas:^7.0`; update `config/canvas.php` to v7's schema.
5. Run `php artisan migrate`: this applies the `rename_canvas_v6_tables_to_backup` migration (renames v6 tables to `canvas_v6_backup_*`, no data loss), then Canvas's own v7 migrations (creates fresh `canvas_*` tables via `canvas:install`), then the `migrate_canvas_v6_content_to_v7` reconciliation migration (re-populates posts/tags/topics/canvas_users access rows from the backup tables, preserving UUIDs).
6. Review the topic-collapse log produced by the reconciliation migration for any post needing manual correction.
7. Remove `SyncCanvasAuth`, the guard override in `CanvasServiceProvider`, and update `@ifcanvasauthenticated`.
8. Smoke-test per Canvas's own checklist (403 for no-access users, admin SPA loads, boot payload shape, media upload/display) plus this app's specifics (`/blog` index, an individual post, comment submission, `/admin/comments` moderation, `canvas:make-admin` granting access).
9. `php artisan up`; monitor.
10. Leave the `canvas_v6_backup_*` tables in the database. They are not cleaned up as part of this change — if the developer later wants them gone, that is a separate, deliberate decision made outside this migration, not an automatic step here.

Rollback strategy: `php artisan migrate:rollback` reverses the reconciliation migration and the rename migration, which restores the original `canvas_*` table names with their original data untouched (since they were only ever renamed, never dropped), then revert the composer/config/code changes via `git revert`. The external SQL dump/media backup from step 3 is a fallback only, not the primary rollback path.
